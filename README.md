# 🍿 YouTube Watch Party

Watch YouTube videos together in real time. When the host plays, pauses, seeks or changes the video, everyone in the room sees the same thing at the same second.

**Live app:** `https://<your-app>.vercel.app`  ·  **API:** `https://<your-api>.onrender.com/api/health`

## Features

- Register / log in (bcrypt password hashing + JWT)
- Create a room (you become **Host**) or join with a code / invite link (you join as **Participant**)
- Synced play, pause, seek and change video over WebSockets (Socket.IO)
- Roles: **Host**, **Moderator**, **Participant**, **Viewer**, enforced on the server
- Host can assign roles, remove participants (they can't re-join) and transfer host
- Participants can *request* an action; host/moderators approve or decline it
- Live chat, participant list with roles, late-joiners land at the correct second
- Rooms persist in MongoDB (name, host, last video)

## Run locally

Requirements: Node 18+, and MongoDB (local or a free Atlas cluster).

```bash
# 1) backend
cd backend
cp .env.example .env        # set MONGO_URI and JWT_SECRET
npm install
npm run dev                 # http://localhost:5000/api/health

# 2) frontend (new terminal)
cd frontend
cp .env.example .env        # VITE_API_URL=http://localhost:5000
npm install
npm run dev                 # http://localhost:5173
```

Test sync by opening the room in a normal window and an incognito window with two different accounts.

## Deploy

### 1. MongoDB Atlas
1. Create a free M0 cluster, a database user, and copy the connection string.
2. Network Access → allow `0.0.0.0/0` (Render's IPs are not fixed on the free plan).

### 2. Backend on Render
1. Push the repo to GitHub.
2. Render → **New → Blueprint** → select the repo (it reads `render.yaml`).
   *Or* New → Web Service with: Root directory `backend`, Build `npm install`, Start `npm start`, Health check `/api/health`.
3. Set env vars: `MONGO_URI`, `CLIENT_URL` (fill in after step 3), `NODE_ENV=production`. `JWT_SECRET` is auto-generated by the blueprint.
4. Copy the URL, e.g. `https://watch-party-api.onrender.com`.

### 3. Frontend on Vercel
1. Vercel → **Add New Project** → import the repo.
2. Root directory: `frontend`. Framework: Vite (auto-detected).
3. Env var: `VITE_API_URL=https://watch-party-api.onrender.com` (no trailing slash).
4. Deploy, then copy the Vercel URL into Render's `CLIENT_URL` and redeploy the backend.
   Several origins are allowed comma-separated: `https://app.vercel.app,http://localhost:5173`.

`frontend/vercel.json` rewrites every path to `index.html`, so refreshing `/room/ABC123` doesn't 404.

### Platform notes
- **Render free tier sleeps after ~15 min idle.** The first request takes ~30–60 s to wake it. Open `/api/health` a minute before a demo.
- Render supports WebSockets on web services. Vercel serverless functions do **not** keep WebSockets open, which is why the socket server lives on Render and Vercel only serves the static React build.
- Vite bakes `VITE_*` variables in at **build time**, so after changing `VITE_API_URL` you must redeploy.

## Architecture: how WebSockets drive the sync

```
 Host browser                 Render (Node)                     Other browsers
 ────────────                 ─────────────                     ──────────────
 click Pause ── 'pause' ───▶  guard(): in room? role allowed?
                              room.pause()  (in-memory state)
              ◀── 'sync_state' { videoId, isPlaying:false, currentTime } ──▶ everyone
 player.pauseVideo()                                           player.pauseVideo()
```

1. **The server is the single source of truth.** Clients never sync with each other; they send *intents* (`pause`) and render whatever `sync_state` the server broadcasts, the sender included.
2. **Time without a ticking clock.** The `Room` stores `position` and `updatedAt` at the last change. When playing, `currentTime = position + (now − updatedAt) / 1000`. A late joiner gets the exact second in `room_joined`.
3. **Client-side drift correction.** The client stores the local time it received the state (`receivedAt`) and every 2 s computes where the video should be. It only seeks if it is off by more than 1.5 s, to avoid stutter. Using the browser's own clock for `receivedAt` avoids server/client clock-skew problems.
4. **No echo loops.** YouTube's built-in controls are disabled and a transparent shield covers the iframe. The only way to control playback is our buttons → server → everyone.
5. **Auth on the socket.** The JWT is sent in the handshake (`io(url, { auth: { token } })`) and verified once in `io.use()`. Every event then knows `socket.data.user`.

### Role-based access control

Defined once in `backend/src/shared/constants/roles.js` as role → permissions:

| Permission | Host | Moderator | Participant | Viewer |
|---|:-:|:-:|:-:|:-:|
| Play / pause / seek / change video | ✅ | ✅ | request only | ❌ |
| Approve participant requests | ✅ | ✅ | ❌ | ❌ |
| Assign roles | ✅ | ❌ | ❌ | ❌ |
| Remove participant | ✅ | ❌ | ❌ | ❌ |
| Transfer host | ✅ | ❌ | ❌ | ❌ |
| Chat | ✅ | ✅ | ✅ | ✅ |

Every socket handler is wrapped in `guard(PERMISSION, handler)`, which rejects the event on the server if the role lacks it. The frontend hides/disables buttons only for UX; editing the frontend in DevTools grants nothing.

## Code walkthrough cheat sheet (for the interview)

**Why REST *and* WebSockets?** Create/lookup room and login are one-off request/response, so REST fits. Playback, roles and chat are pushed by the server to many clients instantly, so WebSockets fit.

**Why Socket.IO over raw `ws`?** Built-in rooms (`io.to(code).emit`), automatic reconnect, heartbeats, fallback to long-polling, and handshake auth. Raw `ws` would need all of that written by hand.

**Where does live state live?** In memory (`roomManager` → `Room` objects), because play/pause/seek happen constantly and must be fast. MongoDB keeps only what must survive a restart (code, name, host, last video).

**OOP in the socket server.** `Room` encapsulates participants, playback and requests behind methods (`play()`, `assignRole()`, `transferHost()`); `Participant` hides `socketId` from clients via `toJSON()`; `roomManager` is a singleton registry that lazy-loads rooms from the DB and avoids double-loading with a promise map.

**Security points.** Passwords hashed with bcrypt (salted, slow). Password field `select: false`. Same error for "no user" and "wrong password". JWT checked on REST *and* on the socket handshake. Every socket event re-validates role and input (video id regex, seek time is a finite number, chat length capped).

**Edge cases handled.** Refresh keeps your role (`savedRoles`). Two tabs of the same user don't kick each other out (`socketId` check on leave). Kicked users can't re-join. Auto-rejoin after reconnect (join on every `connect`). Browser autoplay policy handled with a one-time "Start watching" click. Two people joining an unloaded room at once share one DB load.

**Trade-offs and limits.**
- In-memory state means **one backend instance**; restarting resets live position (video and host are restored from DB).
- localStorage token is simple across two domains but readable by JS; httpOnly cookies would need `SameSite=None; Secure` cross-site setup.
- Sync accuracy is about ±1.5 s by design; tighter tolerance causes visible stutter on slow networks.
- If the host leaves, the room keeps working for moderators; host powers return when the host re-joins.

**How to scale to 1,000+ users / 100+ rooms.** Run several backend instances behind a load balancer with sticky sessions, add the `@socket.io/redis-adapter` so `io.to(room).emit()` reaches sockets on every instance via Redis Pub/Sub, and move `Room` state from memory into Redis hashes so any instance can serve any room.
